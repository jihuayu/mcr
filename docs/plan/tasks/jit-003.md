# jit-003: Complete Windows FS/TLS Native Execution Coverage

## Objective

Replace the current narrow FS-relative rewrite plus host-fault fallback model
with an explicit FS/TLS execution boundary: every guest instruction that uses
the FS segment is classified before native execution, safely materialized when
possible, or forced through an interpreter/trap path before the host CPU can
execute it.

The default Node/V8 JIT smoke is restored, but a deeper Next.js probe reaches a
V8 executable-memory write-scope path where TLS slot state controls page-mutex
locking and unlocking. That path uses FS-relative stores, immediate stores, and
comparisons that are broader than the original fixed-width `mov`/`sub`
materialization set. Depending on host faults is not enough because an
unpatched FS-relative instruction can access mapped host segment state before
MCR can intervene.

## Required Work

1. Decode FS-relative memory operands broadly.
   - Use decoded instruction metadata instead of the current small byte-pattern
     whitelist as the authoritative classifier.
   - Treat any instruction with an FS segment memory operand as requiring either
     materialization or an explicit interpreter/trap marker.
   - Preserve existing fast prefiltering for syscall-only ranges where it does
     not hide FS candidates.

2. Split FS metadata into materialized and interpreted sites.
   - Keep fixed-width absolute rewrites only for forms that are proven safe for
     the current FS base and instruction encoding.
   - Add explicit metadata for non-materializable sites so native entry can
     trap or interpret them before the host executes the original FS-prefixed
     instruction.
   - A missed FS site is a scanner bug and must surface as a diagnostic rather
     than silently falling through to host native execution.

3. Cover the V8 TLS slot instruction family.
   - Register store to FS absolute displacement, including forms like
     `64 4c 89 14 25 e0 ff ff ff`.
   - Compare FS absolute displacement with an immediate, including
     `64 48 83 3c 25 e0 ff ff ff 00`.
   - Immediate store to FS absolute displacement, including
     `64 48 c7 04 25 e0 ff ff ff 00 00 00 00`.
   - Byte/word zero-extension loads such as
     `64 0f b6 04 25 58 fe ff ff`.

4. Keep guest TLS state per task.
   - Re-audit `ARCH_SET_FS`, `ARCH_GET_FS`, `execve`, and supported clone paths
     so the task's `fs_base` is the only guest-visible TLS source.
   - Do not use host Rust TLS or host segment state as guest truth.
   - If `mcr-win` can safely install a zero/sentinel host FS or GS base during
     native execution, keep it as a hardening guard only; correctness must come
     from classification and materialization/trap routing.

5. Add workload-level proof.
   - Keep the existing default Node/V8 optimized JavaScript smoke green.
   - Add a focused ignored probe for the Next.js config-loader path, or document
     the manual fixture setup if the dependency install remains too large for
     committed fixtures.
   - The probe should cover `require("next/dist/server/config")` because it
     reaches the V8 code-memory write-scope cleanup path without needing a full
     `next build`.

The first probe must print the expected marker after
`require("next/dist/server/config")` returns and must not terminate with V8 or
Abseil mutex fatals. The full build remains a follow-up proof after the focused
config-loader contract is stable.

## Non-Goals

- This task does not implement a full cross-architecture x86 interpreter.
- This task does not claim full Node package-manager or Next.js build support
  beyond the focused V8 FS/TLS regression probe.
- This task does not add GS-based guest TLS unless a concrete workload requires
  it; it must avoid designs that block future GS support.
