# net-001: Implement TCP-Client Sockets And Bounded DNS

## Objective

Implement the Phase 2 networking subset: AF_INET/AF_INET6 `SOCK_STREAM` TCP client behavior, socket fd integration, connected stream IO, required socket options, and DNS through `/etc/hosts` plus one bounded resolver path.

## Notes

- The target network architecture is Linux/POSIX socket syscall ABI compatibility
  on Windows, not a direct Winsock wrapper. `net-001` is the first TCP/DNS slice
  of the design in `docs/architecture/networking.md`.
- Cover `socket`, `connect`, stream `sendto`/`recvfrom`, stream `sendmsg`/`recvmsg`, `getsockopt`, `setsockopt`, and `shutdown` as needed by smoke tests.
- Add selected loopback `bind`, `listen`, and `accept` only for smoke tests that require local server behavior; they are not a general server/socket compatibility promise.
- Guest-visible DNS prerequisites now exist through rootfs materialization of `/etc/hosts`,
  `/etc/resolv.conf`, and `/etc/nsswitch.conf` plus UDP datagram socket syscall coverage in
  `mcr-net`/`mcr-runtime`; `net-001` does not require a separate runtime host resolver API.
- Native x86 guest proof for `curl https://example.com` now reaches DNS,
  nonblocking TCP connect completion, TLS certificate verification, and HTTP/2
  200 through the materialized Alpine rootfs. The prior curl exit 7 was socket
  readiness semantics; the later OpenSSL verify result 14/native `hlt` failure
  was traced to reused anonymous mappings not being zero-filled after `munmap`,
  which violated Linux mmap semantics and tripped musl mallocng invariants.
- Remaining validation should extend the same path to `git clone` and keep a
  residual native-execution eye on standalone `openssl verify`, which still
  showed a separate CLI segfault in local diagnostics after curl verification
  succeeded.
- Do not treat Alpine host-shell smoke as proof for this task. Final integration proof now runs through native x86 guest execution, typically via the `x86-runtime-smoke.yml` GitHub Actions workflow or an equivalent x86_64/QEMU environment.
- Rust `std::net` and Windows APIs may be used as host backends, but guest fd allocation, socket flags, sockaddr layout, nonblocking behavior, close-on-exec, and Linux errno mapping remain owned by MCR.
- Do not expose Windows `SOCKET` values as guest fds. Socket objects must live
  behind the shared MCR fd table so `read`, `write`, `close`, `dup`, `fcntl`, and
  future `poll`/`epoll` paths all observe Linux fd semantics.
- The initial backend should stay semantic-first: nonblocking sockets plus
  runtime wait/readiness handling. IOCP, `AcceptEx`, and `ConnectEx` are
  follow-on performance work after the fd, errno, close, sockopt, and readiness
  contracts are stable.
- Raw sockets, packet sockets, network namespaces, firewalling, port publishing, transparent proxy/VPN behavior, and UDP semantics outside the DNS path are unsupported.
- AF_UNIX, `SCM_RIGHTS`, `SO_REUSEPORT`, advanced multicast options, and
  cross-process socket inheritance remain partial or deferred unless a later
  task explicitly expands the compatibility promise.
